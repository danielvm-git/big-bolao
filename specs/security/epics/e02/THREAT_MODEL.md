# Threat Model — e02-s03: BigBase.ensure_setup upsert from API

## Epic scope

Change `BigBase.ensure_setup()` in `bolao/bigbase.py` to:

1. Try `fetch_from_api()` from `bolao/fixtures.py`
2. Upsert fixtures with `api_fixture_id` as dedup key
3. Fall back to hardcoded `MATCHES` if API fails

## Surface area

| Component                          | Role         | Data flow                                           |
| ---------------------------------- | ------------ | --------------------------------------------------- |
| `bolao/bigbase.py:ensure_setup`    | Orchestrator | fetches fixtures → upserts to BigBase               |
| `bolao/fixtures.py:fetch_from_api` | HTTP client  | GET apiv3.apifootball.com → normalise → return list |
| BigBase collection `jogos`         | Data store   | Stores match records with `api_fixture_id`          |

## Risk summary

**Overall: LOW** — no authentication boundary, no user input, read-only external data, CSP mitigates XSS.

| Finding                      | Risk   | Action                                              |
| ---------------------------- | ------ | --------------------------------------------------- |
| API key in URL params        | Accept | Document in comments. Key has read-only scope.      |
| Potential XSS via team names | Accept | CSP already blocks. No HTML rendering of raw names. |

## Mitigations

- **API key hygiene**: Key is env-only, never hardcoded. Already satisfied.
- **HTTPS**: Connection to apifootball.com is HTTPS. Already satisfied.
- **Input validation**: All API data goes through BigBase as strings. BigBase stores JSON — no SQL injection risk.

## Recommendation

Proceed with implementation. No security blocking issues.
